# Changelog

## Unreleased

First release.

- `shapr RANGE` classifies each hunk of `git diff RANGE`; with no range, a unified diff is read from stdin. `-C DIR` runs as if started in DIR, like `git -C`, ignoring an inherited `GIT_DIR`, `GIT_WORK_TREE` or `GIT_INDEX_FILE`.
- Ruby (`.rb`, `.rake`, `.gemspec`, `.ru`, `Gemfile`, `Rakefile`) is parsed with prism and Rust (`.rs`) with tree-sitter; both get every hunk kind. Hunks in other files are `logic` with confidence 0. A file with a syntax error is compared line by line instead (`parsed: false`, confidence at most 0.5).
- `format_only` (same syntax tree, ignoring whitespace) and `comment_only` (same tree, comment text differs). Ruby magic comments and rubocop directives count as code. In Rust, doc comments are comments, attributes are code, and a trailing comma is formatting.
- `rename`: a hunk that only renames identifiers, when every use of each old name in its scope (a local's method, a Ruby field's file, a method's, constant's or Rust struct field's whole change) became the new name and the new name wasn't already there. `detail.renames` lists the pairs; confidence falls where uses can live outside the diff (methods, constants, fields). A leftover `send(:old)`, a keyword-parameter rename, a renamed method that calls `super`, or a Rust rename that leaves the old name inside a macro's arguments stays `logic`.
- `move`: a hunk that only relocates method, class, module or constant definitions, within a file or across files; `move_with_changes` (a behavior kind) when a relocated definition's body also changed. Both halves name each other by hunk `id` in `detail.moves`, with the changed lines of a `move_with_changes`. A definition that moves unchanged but lands among different code is a `move_with_changes` too, with `detail.context` naming what differs: `owner`, `visibility`, `load_order`, `directives`, or `module` (each Rust file is its own module); `summary.move_contexts` counts them. Reordering other statements (callbacks, validations, `include`s) stays `logic`.
- `extract` and `inline`: statements moved into a new method and replaced by a call to it, or the reverse. Matches must be exact after renaming parameters to arguments. A match that would change behavior stays `logic`, with `detail.near` and a `detail.risk`: `jump` (`return`, `yield`, Rust's `?`), `block_parameter` (the caller's block), `wiring` (mismatched arguments), `collision` (a name already in use), `drop` (a Rust value dropped at another point) or `tiny` (a small chunk).
- `-j` and `-J` emit the JSON schema in docs/schema.md: file, hunk and summary records, with code and comment line counts, `review_lines`, and Kamei's diffusion measures.
- `review_lines` counts the code lines a reviewer still has to read: 0 for `format_only`, `comment_only`, `rename` and `move`; only the changed lines inside a `move_with_changes`, plus a moved definition's first line when its context changed; every code line of an `extract`, `inline` or `logic` hunk. `behavior_lines` sums `review_lines` over behavior hunks.
- Lockfiles (`Gemfile.lock`, `Cargo.lock`, `package-lock.json`, `yarn.lock`, `go.sum` and others), `*.min.js`/`*.min.css`, and paths `.gitattributes` marks `linguist-generated` are `generated: true` on file and hunk records. They count toward the verdict (a dependency change is behavior) but not toward `review_lines` or the summary's size measures; `summary.generated_hunks` counts them.
- The exit code carries the verdict: 0 structure (or empty), 1 behavior, 3 mixed; 2 is an error, 64 a usage error. An empty stdin is no input (64), so a failed `git diff` upstream of the pipe is never an empty verdict; stdin with no diff file header is an error (2). Errors are one line: not a git repository, or git's own `bad revision`. Under `-j`/`-J` an error is a JSON record on stdout, except with `-q`, which keeps stdout empty.
- `--completions [SHELL]` prints a completion script for bash, zsh, fish, elvish or PowerShell.
