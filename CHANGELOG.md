# Changelog

## Unreleased

First release.

- `shapr RANGE` classifies each hunk of `git diff RANGE`; with no range, a unified diff is read from stdin. `-C DIR` runs as if started in DIR, like `git -C`, ignoring an inherited `GIT_DIR`, `GIT_WORK_TREE` or `GIT_INDEX_FILE`.
- Ruby (`.rb`, `.rake`, `.gemspec`, `.ru`, `Gemfile`, `Rakefile`) is parsed with prism and Rust (`.rs`) with tree-sitter; both get every hunk kind. Hunks in other files are `logic` with confidence 0. A file with a syntax error is compared line by line instead (`parsed: false`), and the hunk's reason names the side with the error; text can't prove structure, so a hunk whose text matches is `logic` with `detail.near` `format_only` or `comment_only`.
- `format_only` (same syntax tree, ignoring whitespace) and `comment_only` (same tree, comment text differs). Ruby magic comments, rubocop directives and a first-line shebang count as code. A comment moved to another node (a Rust doc comment to another item) is `comment_only`, not `format_only`. In Rust, doc comments are comments but a doctest (fenced code in a doc comment) is code, attributes are code, and a trailing comma is formatting.
- `rename`: a hunk that only renames identifiers, when every use of each old name in its scope (a local's method, a Ruby field's file, a method's, constant's or Rust struct field's whole change) became the new name and the new name wasn't already there. `detail.renames` lists the pairs; confidence falls where uses can live outside the diff (methods, constants, fields). A leftover `send(:old)` (or a computed one that could spell the name: `public_send(name)`, `define_method("get_#{x}")`), a local renamed where `binding` or `eval` can read it, a method that reads its own `__method__`, a keyword-parameter rename, a renamed method that calls `super`, a rename to or from a name the language calls implicitly (Ruby's `to_s`, `initialize`, `each`, `method_missing`, any `Object`/`Kernel` method; Rust's `main`, `drop`, `clone`, `fmt`), a Rust item under an attribute that may read its name (`#[no_mangle]`, `#[pyfunction]`, a route, `#[derive(Debug)]`), or a Rust rename that leaves the old name inside a macro's arguments stays `logic`.
- `move`: a hunk that only relocates method, class, module or constant definitions, within a file or across files; `move_with_changes` (a behavior kind) when a relocated definition's body also changed. Both halves name each other by hunk `id` in `detail.moves`, with the changed lines of a `move_with_changes`. A definition that moves unchanged but lands among different code is a `move_with_changes` too, with `detail.context` naming what differs: `owner`, `visibility`, `load_order` (including a function moved past a `macro_rules!` of a macro it invokes), `directives`, `position` (it reads its own `__LINE__`, or its `__FILE__` across files), or `module` (each Rust file is its own module); `summary.move_contexts` counts them. Reordering other statements (callbacks, validations, `include`s) stays `logic`, and a constant whose value calls something (`X = Counter.next`) keeps its order with the definitions around it (`load_order`).
- `extract` and `inline`: statements moved into a new method and replaced by a call to it, or the reverse. Matches must be exact after renaming parameters to arguments. A match that would change behavior stays `logic`, with `detail.near` and a `detail.risk`: `jump` (`return`, `yield`, Rust's `?`, and code that reads its method's frame or line: `binding`, `eval`, `__method__`, `caller`, `$~`, `__LINE__`), `block_parameter` (the caller's block), `wiring` (mismatched arguments), `collision` (a name already in use, or one the language calls implicitly, such as `inspect` or `hash`), `drop` (a Rust value dropped at another point) or `tiny` (a small chunk).
- `-j` and `-J` emit the JSON schema in docs/schema.md: file, hunk and summary records, with code and comment line counts, `review_lines`, and Kamei's diffusion measures.
- `review_lines` counts the code lines a reviewer still has to read: 0 for `format_only`, `comment_only`, `rename` and `move`; only the changed lines inside a `move_with_changes`, plus a moved definition's first line when its context changed; every code line of an `extract`, `inline` or `logic` hunk. `behavior_lines` sums `review_lines` over behavior hunks.
- Lockfiles (`Gemfile.lock`, `Cargo.lock`, `package-lock.json`, `yarn.lock`, `go.sum` and others), `*.min.js`/`*.min.css`, and paths `.gitattributes` marks `linguist-generated` are `generated: true` on file and hunk records. They count toward the verdict (a dependency change is behavior) but not toward `review_lines` or the summary's size measures; `summary.generated_hunks` counts them.
- The exit code carries the verdict: 0 structure (or empty), 1 behavior, 3 mixed; 2 is an error, 64 a usage error. An empty stdin is no input (64), so a failed `git diff` upstream of the pipe is never an empty verdict; stdin with no diff file header is an error (2). Errors are one line: not a git repository, or git's own `bad revision`. Under `-j`/`-J` an error is a JSON record on stdout, except with `-q`, which keeps stdout empty.
- `facets` on each `logic` hunk say what kind of logic change it is, from the code alone: `test`, `manifest`, `adds_definition`, `removes_definition`, `signature`, `condition`, `error_handling`, `literal_only`. `summary.facets` counts them. They never change a hunk's kind or the verdict. `summary.claims` reports, separately, what the range's commit messages and an optional `--message FILE` description (a PR body; `-` for stdin with a RANGE) claim: conventional-commit types, purpose words in the subject, reverts, issue references, breaking-change and no-behavior-change markers, each with its source, counted per category. `claims.conflicts` lists claims the code doesn't bear out, as counts (a refactor claim with behavior hunks, a fix claim with only structure).
- RANGE may be a GitHub pull request (`https://github.com/o/r/pull/12`, `o/r#12`, or `#12` for this repository's GitHub remote) or commit (`.../commit/SHA`, `.../pull/12/commits/SHA`, `o/r@SHA`): shapr diffs it as GitHub's Files tab does (merge base to head; a commit against its first parent, saying so for a merge) with no checkout. Metadata comes from the GitHub API, using `GH_TOKEN`, `GITHUB_TOKEN` or `gh auth token` when there is one; objects are fetched with your git credentials into a cache of partial clones (`--cache-dir`, `SHAPR_CACHE_DIR`, else `$XDG_CACHE_HOME/shapr`), never into your repository. `--status` shows the cache, `--clear-cache` empties it. `summary.source` names the pull request or commit, `null` for local input. Claims read a pull request's commit messages and its title and body (source `pull_request`; `--message` replaces the body), or a commit's message.
- `--completions [SHELL]` prints a completion script for bash, zsh, fish, elvish or PowerShell.
