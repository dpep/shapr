# Changelog

## Unreleased

First release.

- `shapr RANGE` classifies each hunk of `git diff RANGE`; with no range, a unified diff is read from stdin. `-C DIR` runs as if started in DIR, like `git -C`, ignoring an inherited `GIT_DIR`, `GIT_WORK_TREE` or `GIT_INDEX_FILE`.
- Ruby (`.rb`, `.rake`, `.gemspec`, `.ru`, `Gemfile`, `Rakefile`) is parsed with prism and Rust (`.rs`) with tree-sitter; both get every hunk kind. Hunks in other files are `logic` with confidence 0. A file with a syntax error is compared line by line instead (`parsed: false`), and the hunk's reason names the side with the error (code nested deeper than 10,000 levels isn't compared at all: its hunks are `unknown`, and the reason says why); text can't prove structure, so a hunk whose text matches is `logic` with `detail.near` `format_only` or `comment_only`.
- Each hunk is a list of `parts`: every structural change shapr proves in it, with the before and after lines it explains, and a residual `logic` part holding exactly the lines no proven part explains, so a rename and an edit in one hunk are a `rename` part and the edited line. Each part is proven against the whole change, residual included, and parts never share a line. A hunk that isn't all structure is also classified run by run (each stretch of changed lines between context lines), so a reformat or a comment fix a few lines from a logic edit, which diff context puts in the same hunk, is its own part; code re-indented under a wrapper another run adds stays `logic`. The hunk's `kind` (`logic` unless it is all structure, else its most substantial part kind) and `verdict` roll them up; `confidence`, `reason`, `evidence` (with `comparison`: `ast`, `line` or `none`), `detail` and `facets` are per part.
- `format_only` (same syntax tree, ignoring whitespace) and `comment_only` (same tree, comment text differs). Ruby magic comments, rubocop directives, a first-line shebang, and the encoding comment Ruby scans on line 1 (line 2 after a shebang), such as a vim modeline's `fileencoding=`, count as code. A comment moved to another node (a Rust doc comment to another item) is `comment_only`, not `format_only`. In Rust, doc comments are comments but a doctest (a fenced or indented code block in a doc comment, by rustdoc's Markdown rules) is code, attributes are code, and a trailing comma is formatting. Beside logic, a line git deletes and re-adds unchanged (an `else` between swapped branch bodies) is read with the logic, not as a reformat.
- `rename`: identifiers renamed, when every use of each old name in its scope (a local's method, a Ruby field's file, a method's, constant's or Rust struct field's whole change) became the new name and the new name wasn't already there or defined by new code elsewhere. `detail.renames` lists the pairs; confidence falls where uses can live outside the diff (methods, constants, fields). A leftover `send(:old)` (or a computed method name that could spell it: `public_send(name)`, `define_method("get_#{x}")`), a local renamed where `binding` or `eval` can read it, a method that reads its own `__method__`, a keyword-parameter rename, a renamed method that calls `super`, a rename to or from a name the language calls implicitly (Ruby's `to_s`, `initialize`, `each`, `method_missing`, any `Object`/`Kernel` method; Rust's `main`, `drop`, `clone`, `fmt`), a Rust item under an attribute that may read its name (`#[no_mangle]`, `#[pyfunction]`, a route, `#[derive(Debug)]`), a Rust rename that leaves the old name inside a macro's arguments, one through field-init shorthand (`S { a }` names the field and the local at once), or one through a macro that may spell its tokens out as text (`stringify!`, `dbg!`, a message-less `assert!`, any macro outside std) stays `logic`.
- Proof status: a part is structure only when it is proven, with nothing assumed; each part lists its `assumptions` (`unseen_uses`, `search_capped`, `public_api`, `ambiguous_match`) and `summary.assumptions` counts them. A rename, an extract's new method or an inline's removed method is checked against the whole repository at the change's after revision (`git grep -w`, plus every file of the language that calls a method by a computed name such as `send(n)`; in a GitHub change's cached partial clone, the blobs are fetched in one request first): a file outside the change still using the name makes it `logic`, with the file named in the reason, and the name in a file shapr can't parse for a use (YAML, JavaScript; not docs) leaves `unseen_uses`; against the working tree, untracked files are searched too; and `evidence.searched` counts the files read. A rename or inline of a library's public definition (a gem's `lib/`, a `pub` item of a Rust library crate not marked `publish = false` or `publish = []`, itself or through `publish.workspace = true`, or of one whose `Cargo.toml` can't be read) is `public_api`, so `behavior`: callers outside the repository can break. A move whose unit matched several others equally well is `ambiguous_match`. A diff on stdin is searched in the index when it is staged (`git diff --staged`), in the working tree when it ends there (`git diff`, `git diff HEAD`), and not at all otherwise (`unseen_uses`; give the range instead). A part with assumptions has `structure: false` and its lines count toward `review_lines`.
- `restyle`: code that changed only between spellings of the same program, proven on the trees: the frontend reduces each syntax with equivalent spellings to a canonical form, and the part holds the changed lines whose code is equal in canonical form. Ruby: quote style, symbol quoting, hash syntax (`=>` vs labels, `{x:}` for a local), `%w`/`%i` vs brackets, numeric literal spelling, trailing commas, redundant parentheses, call and `def` parentheses, `a::b`, `.()`, `not`, block delimiters on the same call, `and`/`&&` where the parse is the same, modifier and ternary conditionals, endless defs. Rust: field-init shorthand, redundant parentheses. Look-alikes the parser resolves differently (`puts foo(a) do … end`, `ok = a and b`, `{"a": 1}` vs `{"a" => 1}`, do-while) stay `logic`. `detail.variants` names the variants by the RuboCop cop (or rustfmt option or lint) that chooses among them. It ranks between `comment_only` and `rename` in a hunk's `kind`.
- `move`: method, class, module or constant definitions relocated, within a file or across files; lines of a relocated body that also changed are `logic` beside the `move` part. Both halves name each other by hunk `id` in `detail.moves`, with the changed lines. A definition that moves unchanged but lands among different code is a `move` part that isn't structure, with `detail.context` naming what differs: `owner`, `visibility`, `load_order` (including a function moved past a `macro_rules!` of a macro it invokes), `directives`, `position` (it reads its own `__LINE__`, or its `__FILE__` across files), or `module` (each Rust file is its own module); `summary.move_contexts` counts them. Reordering other statements (callbacks, validations, `include`s) stays `logic`, and a constant whose value calls something (`X = Counter.next`) keeps its order with the definitions around it (`load_order`).
- `extract` and `inline`: statements moved into a new method and replaced by a call to it, or the reverse; an edit to a sibling in the same hunk stays `logic` beside it. Matches must be exact after renaming parameters to arguments. A match that would change behavior stays `logic`, with `detail.near` and a `detail.risk`: `jump` (`return`, `yield`, Rust's `?`, and code that reads its method's frame or line: `binding`, `eval`, `__method__`, `caller`, `$~`, `__LINE__`), `block_parameter` (the caller's block), `wiring` (mismatched arguments), `collision` (a name already in use, or one the language calls implicitly, such as `inspect` or `hash`), `drop` (a Rust value dropped at another point) or `tiny` (a small chunk).
- `-j` and `-J` emit the JSON schema in docs/schema.md: a leading `meta` record (schema and shapr version), then file, hunk and summary records, with code and comment line counts, `review_lines`, part counts per kind (`summary.kinds`), and Kamei's diffusion measures.
- `review_lines` counts the code lines a reviewer still has to read: every code line of the residual, an `extract` or an `inline`; a moved definition's first line when it lands among different code or matched ambiguously; every code line of a rename that isn't proven; none of a `format_only`, `comment_only`, proven `rename` or other `move` part, nor of a hunk whose verdict is `none`. `behavior_lines` sums it over parts that aren't structure, in hunks that count toward the verdict.
- Every file has one `category`, on file and hunk records: `code`, `test`, `docs`, `config`, `manifest`, `generated`, `vendored`, `binary` or `unknown`, by path (top-level `vendor/`, `third_party/` and `node_modules/` are `vendored`) and by the `linguist-generated`, `linguist-vendored` and `linguist-documentation` attributes in `.gitattributes` as of the revision the change ends in (which win over the name either way; a change can't hide its own code edit: code moved into `vendor/`, or marked `linguist-generated` as it is edited, stays `code`). Category is apart from parsing: a Ruby spec is `test`, and still parsed. Lockfiles, minified assets and vendored files don't count toward `review_lines` or the summary's size measures; `summary.categories` counts hunks per category.
- Verdicts count only code, test, config and manifest files. A hunk's `verdict` is `structure`, `behavior` or `mixed` there; `none` for docs and for trailing-whitespace or blank-line edits in a file shapr doesn't parse; `unknown` for generated, vendored, binary and unknown files, and code shapr couldn't read. The change's verdict rolls up the counted hunks: a README-only change is `none`, a docs edit never makes a change `behavior`, a config change is `behavior`, and a lockfile-only change is `unknown`. `summary.verdicts` counts hunks per verdict; `summary.test_review_lines` splits test code out of `review_lines`.
- Exit codes: 0 on success whatever the verdict (the verdict is in the output), 2 an error, 64 a usage error. An empty stdin is no input (64), so a failed `git diff` upstream of the pipe is never a `none` verdict; stdin with no diff file header is an error (2). A merge against all its parents (`R^!` on a merge, or a combined `diff --cc` on stdin) is an error (2) that says to diff against one parent (`R^1..R`). Errors are one line: not a git repository, or git's own `bad revision`. Under `-j`/`-J` an error is a JSON record on stdout, carrying `schema`, except with `-q`, which keeps stdout empty.
- `facets` on each residual say what kind of logic change its lines are, from the code alone: `test` (a Rust test item; a test file is a category), `adds_definition`, `removes_definition`, `signature`, `condition`, `error_handling`, `literal_only`. `summary.facets` counts them. They never change a hunk's kind or the verdict. `summary.claims` reports, separately, what the range's commit messages and an optional `--message FILE` description (a PR body; `-` for stdin with a RANGE) claim: conventional-commit types, purpose words in the subject, reverts, issue references, breaking-change and no-behavior-change markers, each with its source. `claims.experimental` (unstable before 1.0) counts messages per claimed category and lists `conflicts`, claims the code doesn't bear out, as counts (a refactor claim with behavior hunks, a fix claim with only structure).
- Experimental (may change before 1.0): RANGE may be a GitHub pull request (`https://github.com/o/r/pull/12`, `o/r#12`, or `#12` for this repository's GitHub remote) or commit (`.../commit/SHA`, `.../pull/12/commits/SHA`, `o/r@SHA`): shapr diffs it as GitHub's Files tab does (merge base to head; a commit against its first parent, saying so for a merge) with no checkout. Metadata comes from the GitHub API, using `GH_TOKEN`, `GITHUB_TOKEN` or `gh auth token` when there is one; objects are fetched with your git credentials into a cache of partial clones (`--cache-dir`, `SHAPR_CACHE_DIR`, else `$XDG_CACHE_HOME/shapr`), never into your repository. `--status` shows the cache, `--clear-cache` empties it. `meta.source` names the pull request or commit, `null` for local input. Claims read a pull request's commit messages and its title and body (source `pull_request`; `--message` replaces the body), or a commit's message.
- Experimental: style norms. Each Ruby hunk's `style` says how its new code sits against the quote style (`Style/StringLiterals`) inferred from the unchanged code around it (method, class, file, or for a new file its directory): `aligned`, `converging` (`normalizing` toward the norm, or `renorming` when the whole scope moved), `diverging` or `abstain`, with each deviation's line, column and a unified-diff fix. A string carried over or edited in place keeps its quotes and isn't judged. A norm needs `(n + 1) / (total + 2)` of at least `--norm-threshold` (default 0.8); with none inferred, `.rubocop.yml`'s configured style is expected, and both are always reported. A norm is `restyle` when the hunk's `restyle` part respells its variant, and a restyle away from the norm is `flagged`. Generated, vendored and docs files are skipped. `shapr norms FILE...` reports a file's norms with no diff.
- Experimental: norms read `.rubocop.yml` and a new file's neighbors from the revision a range ends in, or a GitHub change's head, so a historical or remote change is judged against its own config; the working tree only when the change ends there.
- Experimental: the `Layout/SpaceInsideHashLiteralBraces` norm, `space` or `no_space` inside a hash literal's braces.
- Experimental: the `Style/TrailingCommaInArrayLiteral` and `Style/TrailingCommaInHashLiteral` norms, a trailing comma or none in a multiline literal with an item per line.
- Experimental: the `Style/TrailingCommaInArguments` norm, the same for a multiline call's arguments, apart from literals.
- Experimental: the `Style/HashSyntax` norm, `ruby19` labels or `hash_rockets`, per pair.
- Experimental: the `Layout/IndentationConsistency` norm, methods after `private` or `protected` at the modifier's column or a step deeper.
- Experimental: `.editorconfig` configures norms beside `.rubocop.yml`, which wins where both set one. The `Layout/TrailingWhitespace` norm, configured by `trim_trailing_whitespace`.
- Experimental: the `Layout/TrailingEmptyLines` norm, how a file ends, configured by `insert_final_newline`. A suggested edit marks a last line with no line break as unified diffs do.
- Experimental: the `Layout/IndentationWidth` norm, a body's indentation in spaces, configured by RuboCop's `Width` or `.editorconfig`'s `indent_size`.
- Experimental: the `Naming/MethodName` norm, `snake_case` or `camelCase` method names; a rename is suggested only for a private method whose calls are all in the hunk.
- Experimental: the `Naming/VariableName` norm, `snake_case` or `camelCase` local variables, with a rename when every mention of the local is in the hunk.
- Experimental: the `Layout/SpaceAroundOperators` norm, whitespace on both sides of binary operators and assignments; aligned operators count as spaced.
- Experimental: the `Layout/EmptyLineBetweenDefs` norm, a blank line between adjacent method definitions or none.
- `--completions [SHELL]` prints a completion script for bash, zsh, fish, elvish or PowerShell.
