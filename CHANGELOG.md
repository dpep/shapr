# Changelog

## Unreleased

First release.

- Every input form is a git command: `shapr REV` classifies that commit against its first parent (`git show REV`; a merge commit is refused, naming `REV^1..REV` and `REV^2..REV`); `shapr A..B` and `shapr A B` are `git diff A..B`; `shapr A...B` and `shapr main...` diff from the merge base; `shapr --merge-base REF [REV]` is `git diff --merge-base REF [REV]`, without REV the branch's committed and uncommitted work; `shapr PATH...` and `shapr .` are the uncommitted changes to those paths (`git diff HEAD -- PATH`); `shapr --staged [REV]` (or `--cached`) is the index against HEAD or REV (`git diff --cached`), with uses searched in the index; any form takes paths after its revisions (`shapr main..HEAD -- lib`). Arguments are read as git reads them: a name that is both a revision and a path is a usage error (64) asking for `--`. With no arguments, a unified diff is read from stdin. `meta.input` names the form and `meta.paths` whether paths limited it. A form ending in the working tree leaves untracked files out, as `git diff` does; shapr names them on stderr with the `git add -N` that includes them, and counts them in `meta.untracked`. `shapr main` is now main's last commit, no longer main against the working tree: retype `shapr main...` for a branch's commits, `shapr --merge-base main` for everything on the branch, committed or not, and `git diff main | shapr` for main against the working tree. `-C DIR` runs as if started in DIR, like `git -C`, before or after `norms`, ignoring an inherited `GIT_DIR`, `GIT_WORK_TREE` or `GIT_INDEX_FILE`.
- Ruby (`.rb`, `.rake`, `.gemspec`, `.ru`, and the DSL files RuboCop includes: `Gemfile`, `Rakefile`, `Guardfile`, `Podfile`, `Vagrantfile` and the like) is parsed with prism and Rust (`.rs`) with tree-sitter; both get every hunk kind. Hunks in other files are `logic` with confidence 0. A file with a syntax error is compared line by line instead (`parsed: false`), and the hunk's reason names the side with the error (code nested deeper than 10,000 levels, or a file too big to compare, whose changed lines pass 8,000 or changed bytes 192,000, or whose size squared takes the change past 256,000,000, charged smallest file first, or with a side over 4 MiB or a node too wide to align, isn't compared at all: its hunks are `logic`, inside the verdict, and the reason says why); text can't prove structure, so a hunk whose text matches is `logic` with `detail.near` `format_only` or `comment_only`.
- Each hunk is a list of `parts`: every structural change shapr proves in it, with the before and after lines it explains, and a residual `logic` part holding exactly the lines no proven part explains, so a rename and an edit in one hunk are a `rename` part and the edited line. Each part is proven against the whole change, residual included, and parts never share a line. A hunk that isn't all structure is also classified run by run (each stretch of changed lines between context lines), so a reformat or a comment fix a few lines from a logic edit, which diff context puts in the same hunk, is its own part; code re-indented under a wrapper another run adds stays `logic`. The hunk's `kind` (`logic` unless it is all structure, else its most substantial part kind) and `verdict` roll them up; `confidence`, `reason`, `evidence` (with `comparison`: `ast`, `line` or `none`), `detail` and `facets` are per part.
- `rename`: identifiers renamed, when every use of each old name in its scope (a local's method, a Ruby field's file, a method's, constant's or Rust struct field's whole change) became the new name and the new name wasn't already there or defined by new code elsewhere, in the change or (for a method, constant or field) anywhere in the repository: renaming onto a name an unchanged file holds (a parent's method, a subclass's instance variable, a call to another method of that name) is `logic`. Classes and modules (Rust structs, enums, unions, traits, `mod`s) rename by the same rule, `public_api` in a library's public surface; code that reads a type's name at runtime (`Class#name`, `std::any::type_name`) sees the new one. `detail.renames` lists the pairs, each with the occurrences that part holds (they sum over parts to the change's); confidence falls where uses can live outside the diff (methods, constants, fields). A leftover `send(:old)` (or a computed method name that could spell it: `public_send(name)`, `define_method("get_#{x}")`; for a class or constant, a computed lookup: `const_get(name)`, `name.constantize`; for an instance or class variable, `instance_variable_get(name)` and its kin), a local renamed where `binding` or `eval` can read it, a method that reads its own `__method__`, a keyword-parameter rename, a renamed method that calls `super`, a renamed class or module in a Ruby repository that autoloads by file name (Zeitwerk, Rails), a public method of a Rails application's or engine's controller, mailer, job or channel (any `app/controllers/`, `app/mailers/`, `app/jobs/` or `app/channels/` at any depth in a repository holding a `config/application.rb` or an `engine.rb` anywhere: packs and engines included) (routes and `perform_later` call it by name) or a Rust `mod name;` (whose file keeps its name), a rename to or from a name the language calls implicitly (Ruby's `to_s`, `initialize`, `each`, `method_missing`, `deconstruct_keys`, an exception's `message`, an IO-like object's `write`, any `Object`/`Kernel` method; Rust's `main`, `drop`, `clone`, `fmt`), a Rust item under an attribute that may read its name (`#[no_mangle]`, `#[pyfunction]`, a route, `#[derive(Debug)]`), any rename inside a Rust item (or its `impl` or `mod`) under an attribute macro, which reads the item's tokens (an attribute off a short inert std list, a derive outside std), a Rust rename that leaves the old name inside a macro's arguments or a doctest (whose lines a rename never passes through), one through shorthand that names a member and a local at once (Rust's `S { a }` and `S { mut a }`, inside a macro's tokens any name directly in braces; Ruby's `g(x:)` and `{x:}`), or one through a macro that may spell its tokens out as text (`stringify!`, `dbg!`, a message-less `assert!`, any macro outside std) stays `logic`.
- `format_only` (same syntax tree, ignoring whitespace) and `comment_only` (same tree, comment text differs). Ruby magic comments, rubocop directives, a first-line shebang, and the encoding comment Ruby scans on line 1 (after any byte order mark; line 2 after a shebang), such as `# coding = binary` or a vim modeline's `fileencoding=`, count as code. A comment moved to another node (a Rust doc comment to another item) is `comment_only`, not `format_only`. In Rust, doc comments are comments but a doctest (a fenced or indented code block in a doc comment, by rustdoc's Markdown rules, across the plain comments, attributes and blank lines rustdoc joins an item's doc comments over) is code, as is a doc comment a macro may read (in a macro's arguments, or on or inside an item under a derive outside std or an attribute macro, such as a CLI parser's help text), while a fence naming only another language (```text) is a comment, attributes are code, and a trailing comma is formatting (in a macro's arguments only `vec!`'s); whitespace inside the arguments of a macro that may spell its tokens out (`stringify!`, `dbg!`, a message-less `assert!`, any macro outside std) is code. A hunk that moves code reading its own position (`__LINE__`, `line!()`, `column!()`, `dbg!`) or the call stack (`caller`, `caller_locations`, also on `Kernel`, `Thread.current.backtrace_locations`, `Location::caller()`), by holding it or by adding or removing lines above it, proves no structure, unless the read keeps its line and column (an edit after it on its own line) (`detail.near` names the kind). Beside logic, a line git deletes and re-adds unchanged (an `else` between swapped branch bodies) is read with the logic, not as a reformat.
- Proof status: a part is structure only when it is proven, with nothing assumed; each part lists its `assumptions` (`unseen_uses`, `search_capped`, `public_api`, `ambiguous_match`) and `summary.assumptions` counts them. A rename, an extract's new method or an inline's removed method is checked against the whole repository at the change's after revision (`git grep -w`, plus every file of the language that calls a method by a computed name such as `send(n)`; in a GitHub change's cached partial clone, the blobs are fetched in one request first): a file outside the change still using the name makes it `logic`, with the file named in the reason, and the name in a file shapr can't parse for a use (YAML, JavaScript; not docs) leaves `unseen_uses`; against the working tree, untracked files are searched too; and `evidence.searched` counts the files read. A rename or inline of a library's public definition (a gem's `lib/`, a `pub` item of a Rust library crate not marked `publish = false` or `publish = []` in `[package]`, itself or through `publish.workspace = true`, or of one whose `Cargo.toml` can't be read) is `public_api`, so `behavior`: callers outside the repository can break. A move whose unit matched several others equally well is `ambiguous_match`. A diff on stdin is searched in the index when it is staged (`git diff --staged`), in the working tree when it ends there (`git diff`, `git diff HEAD`), in both when its blob ids fit both, and not at all otherwise (`unseen_uses`; give the range instead). A part with assumptions has `structure: false` and its lines count toward `review_lines`.
- `restyle`: code that changed only between spellings of the same program, proven on the trees: the frontend reduces each syntax with equivalent spellings to a canonical form, and the part holds the changed lines whose code is equal in canonical form. Ruby: quote style, symbol quoting, hash syntax (`=>` vs labels, `{x:}` for a local), `%w`/`%i` vs brackets, numeric literal spelling, trailing commas, redundant parentheses, call and `def` parentheses, `a::b`, `.()`, `not`, block delimiters on the same call, `and`/`&&` where the parse is the same, modifier and ternary conditionals, endless defs. Rust: field-init shorthand, redundant parentheses, the order of a braced `use` list. Look-alikes the parser resolves differently (`puts foo(a) do … end`, `ok = a and b`, `{"a": 1}` vs `{"a" => 1}`, do-while) stay `logic`. `detail.variants` names the variants by the RuboCop cop (or rustfmt option or lint) that chooses among them. It ranks between `comment_only` and `rename` in a hunk's `kind`.
- `reorder`: a hunk's elements of one container are the same code in another order. Structure for Rust items and separate `use` declarations (no `macro_rules!`, `#[macro_use]`, item macro or attribute macro beside them) and a struct literal's plain fields; otherwise `structure: false` with `detail.context` naming what observes the order: `load_order` (`require`s, Gemfile `gem` lines, gemspec dependencies), `iteration_order` (Ruby hash entries), `element_order` (arrays, struct field declarations) or `evaluation_order` (statements, values that call code). A reorder beside an edit is a `reorder` part and the edited lines.
- `default_argument`: a call drops or adds an argument that restates its parameter's literal default (`fetch(x, retries: 3)` and `fetch(x)` where `fetch` says `retries: 3`), Ruby only. The call has no receiver but `self` and no block around it inside its method; the method it calls is defined once in the repository, in the same class or module body and on the same receiver, takes no `*args`, `**opts` or `...`, and nothing else names it (`send`, `alias`, `define_method`, a symbol); the argument and the default are the same integer, float, symbol, plain string, `nil`, `true`, `false`, `{}` or `[]`, compared as `restyle` compares them. Anything else, such as a call on another object or a default that is an expression, stays `logic`; a method in a gem's `lib/` is `public_api`. `detail.restated` names each argument. Where a call isn't proven, the residual's reason names each such call and why (a receiver, an argument shapr can't tie to a parameter, another definition that may override the method, the file where something else names it). It ranks between `restyle` and `rename` in a hunk's `kind`.
- `move`: method, class, module or constant definitions relocated, within a file or across files (two swapped ones too, whichever git shows moving); lines of a relocated body that also changed are `logic` beside the `move` part. Both halves name each other by hunk `id` in `detail.moves`, with the changed lines. A definition that moves unchanged but lands among different code is a `move` part that isn't structure, with `detail.context` naming what differs: `owner`, `visibility`, `load_order` (including a function moved past a `macro_rules!` of a macro it invokes, or past an item macro), `directives`, `position` (it reads its own `__LINE__`, or its `__FILE__` across files), or `module` (each Rust file is its own module); `summary.move_contexts` counts them. Reordering other statements (callbacks, validations, `include`s) stays `logic`, a constant whose value calls something (`X = Counter.next`) keeps its order with the definitions around it, and a Ruby method keeps its order with any statement that runs code at load time (`include`, `extend T::Sig`, `undef_method`, a `class << self`) and with a `method_added` hook (below one, with every other method too), within a file or into a new one (`load_order`). A definition moved into a new file pairs with what it left, inside the namespaces the new file opens (`module Zoo`, a reopened `class Cart`); in Ruby it is structure only when the new file is shown to run the code where it ran: the old file `require`s it at its top level, or every load of the old file is directly followed by one of the new (in a gem's `lib/`, `public_api`), with no `require` of a computed path anywhere in the repository; otherwise `load_order`.
- `extract` and `inline`: statements moved into a new method and replaced by a call to it, or the reverse; an edit to a sibling in the same hunk stays `logic` beside it, but a `private` line added (or removed) for the new method alone belongs to it. Matches must be exact after renaming parameters to arguments. A match that would change behavior stays `logic`, with `detail.near` and a `detail.risk`: `jump` (`return`, `yield`, Rust's `?`, code that reads its method's frame or line: `binding`, `eval`, `__method__`, `caller`, `$~`, `__LINE__`, and in Ruby statements or a call inside a block, which may run with another `self`), `block_parameter` (the caller's block), `wiring` (mismatched arguments), `collision` (a name already in use, or one the language calls implicitly, such as `inspect` or `hash`), `drop` (a Rust value dropped at another point) or `tiny` (a small chunk).
- `-j` and `-J` emit the JSON schema in docs/schema.md: a leading `meta` record (schema, shapr version, and `command`: `classify` or `norms`, so a gate reading `summary.verdict` can tell a `shapr norms` output, which has none), then file, hunk and summary records, with code and comment line counts, `review_lines`, part counts per kind over the hunks inside the verdict (`summary.kinds`), and Kamei's diffusion measures.
- `review_lines` counts the code lines a reviewer still has to read: every code line of the residual (every changed line of one holding only comments or blank lines), an `extract` or an `inline`; a moved definition's first line when it lands among different code or matched ambiguously; every code line of a rename that isn't proven; none of a `format_only`, `comment_only`, proven `rename` or other `move` part, nor of a hunk whose verdict is `none`. `behavior_lines` sums it over parts that aren't structure, in hunks that count toward the verdict.
- Every file has one `category`, on file and hunk records: `code`, `test`, `docs`, `fixture`, `config`, `manifest`, `generated`, `vendored`, `binary` (by content, in a language shapr doesn't parse: a Ruby or Rust file holding a NUL, or an attribute such as `-diff` that makes git call a text file binary, doesn't, and shapr diffs it again as text) or `unknown`, by path (top-level `vendor/`, `third_party/` and `node_modules/` are `vendored`) and by the `linguist-generated`, `linguist-vendored` and `linguist-documentation` attributes in `.gitattributes` as of the revision the change ends in (which win over the name either way; a change can't hide its own code edit: code moved into `vendor/`, marked `linguist-generated` as it is edited, or added and marked generated, vendored or documentation in one change, stays `code`; a file a change adds under `vendor/` or `fixtures/` is still `vendored` or `fixture` by name). Category is apart from parsing: a Ruby spec is `test`, and still parsed. Lockfiles, minified assets and vendored files don't count toward `review_lines` or the summary's size measures; `summary.categories` counts hunks per category.
- Verdicts count only code, test, config and manifest files. A hunk's `verdict` is `structure`, `behavior` or `mixed` there; `none` for docs, for fixtures (files under a `fixtures/`, `__fixtures__/` or `testdata/` directory at any depth: test data, not parsed or classified, with no lines to review, unless binary, vendored or marked by a linguist attribute; `shapr norms` skips them too), and for trailing-whitespace or blank-line edits in a file shapr doesn't parse; `unknown` for generated, vendored, binary and unknown files and tests in a language shapr doesn't parse. A code, test, config or manifest file shapr didn't compare (no parser for config, a cap, unreadable) is `behavior`: what shapr didn't compare never leaves the verdict on its own say. The change's verdict rolls up the counted hunks: a README-only change is `none`, a docs edit never makes a change `behavior`, a config change is `behavior`, and a lockfile-only change is `unknown`. `summary.verdicts` counts hunks per verdict; `summary.test_review_lines` splits test code out of `review_lines`.
- A usage log: each `classify` or `norms` run appends one JSON line to `$XDG_STATE_HOME/shapr/usage.jsonl` (else `~/.local/state/shapr/usage.jsonl`) with the command, input form, flag names, format, exit code, duration and counts, never paths, repositories, revisions, code, messages or URLs. Set `SHAPR_USAGE=0` (`false`, `off`, `no`) to turn it off, `1` (`true`, `on`, `yes`) to turn it on, or an absolute path to move it; CI (`CI` set to `true`, `1`, `yes` or `on`, or `GITHUB_ACTIONS=true`) turns it off unless `SHAPR_USAGE` is set. The log is created private (0600), never written through a symlink, and trimmed in place under a lock, so concurrent runs keep its newest half. `shapr --usage` summarizes it, `--usage --reset` empties it, and `--status` shows where it is.
- Exit codes: 0 on success whatever the verdict (the verdict is in the output), 2 an error, 64 a usage error. An empty stdin is no input (64), so a failed `git diff` upstream of the pipe is never a `none` verdict; stdin with no diff file header is an error (2). A merge against all its parents (`shapr R` or `R^!` on a merge, or a combined `diff --cc` on stdin) is an error (2) that says to diff against one parent (`R^1..R`). A GitHub file or directory page (`/blob/`, `/tree/`) is a usage error (64) saying a file isn't a change. Errors are one line: not a git repository, `NAME: no such revision or path`, or git's own message. A name that is both a revision and a path gives both commands, ready to run: `shapr lib --` for the revision, `shapr -- lib` for the path. In a shallow clone, a change whose base commit wasn't fetched (`shapr HEAD` at depth 1, `main...HEAD` with no merge base) is an error (2) saying so and naming `fetch-depth: 0`, never a commit read as if it had no parent. A bug that panics is an error too (2, `internal error: ..., please report it`), never another exit code. Under `-j`/`-J` an error is a JSON record on stdout, carrying `schema`, except with `-q`, which keeps stdout empty.
- Untrusted repositories (a CI gate on fork pull requests): git never runs a program the repository names (`core.fsmonitor`, hooks), and never fetches into a repository whose own config could name a program, since a fetch runs what it names (`remote.*.uploadpack`, `core.sshCommand`, a credential helper): a partial clone whose `.git/config` holds only what an ordinary clone writes (core settings, remotes with plain URLs, branches, the partial-clone keys) fetches the blobs the diff needs from its promisor remote, as git would; one setting anything else makes a blob the diff needs and the clone lacks an error (2) naming the key, so check out without a filter; shapr needs git 2.24 or later, 2.44 to refuse that fetch, and an older git is an error (2) naming its version; system and global git config still apply. A revision starting with `-` (`--merge-base=--output=FILE`) is a usage error (64), as is one revision that isn't one commit (`REV^{tree}`, `REV:PATH`, `REV^@`), and git is told where its options end before every revision. Text output and stderr escape control characters C-style (a file name holding a newline can't start a `::error::` workflow command or send a terminal escape), and quote such a path as git does (`"lib/y\n.rb"`); JSON was already escaped. The README's CI recipe allowlists verdicts (anything else fails the gate), passes the base branch through `env:`, warns on hunks outside the verdict, and caps the log.
- `facets` on each residual say what kind of logic change its lines are, from the code alone: `test` (a Rust test item; a test file is a category), `adds_definition`, `removes_definition`, `signature`, `condition`, `error_handling`, `literal_only`. `summary.facets` counts them. They never change a hunk's kind or the verdict. `summary.claims` reports, separately, what the range's commit messages and an optional `--message FILE` description (a PR body; `-` for stdin with a RANGE) claim: conventional-commit types, purpose words in the subject, reverts, issue and pull request references (a bare `#N` is a neutral `reference` unless GitHub input looks it up; schema change: `issue` no longer covers it), breaking-change, no-behavior-change (including a subject closing on ", unchanged") and test-only markers, each with its source; purpose words inside a path or identifier, or denied (`not a rename`), claim nothing, and a pull request title repeating its commit's subject claims it once. Lint and format words (`rubocop`, `autocorrect`, `lint`, `reformat`, the `style:` type) claim `style`, and so does the `fix` in "Fix lint errors". `claims.experimental` (unstable before 1.0) counts messages per claimed category and lists `conflicts`, claims the code doesn't bear out, with the ids of the hunks behind each (a refactor claim with hunks not shown structural, outside tests when a message also claims a test change; a style claim with logic hunks in code or tests; a reorder claim with no reorder or move part; a fix claim with only structure).
- Experimental (may change before 1.0): the argument may be a GitHub pull request (`https://github.com/o/r/pull/12`, `o/r#12`, or `#12` for this repository's GitHub remote) or commit (`.../commit/SHA`, `.../pull/12/commits/SHA`, `o/r@SHA`): shapr diffs it as GitHub's Files tab does (merge base to head; a commit against its first parent, saying so for a merge) with no checkout. Metadata comes from the GitHub API, using `GH_TOKEN`, `GITHUB_TOKEN` or `gh auth token` when there is one; objects are fetched with your git credentials into a cache of partial clones (`--cache-dir`, `SHAPR_CACHE_DIR`, else `$XDG_CACHE_HOME/shapr`), never into your repository. Runs at once on one cached repository take turns (a lock file in the clone) rather than fail on git's locks. `--status` shows the cache, `--clear-cache` empties it. `meta.source` names the pull request or commit, `null` for local input. Claims read a pull request's commit messages and its title and body (source `pull_request`; `--message` replaces the body), or a commit's message.
- Experimental: style norms. Each Ruby hunk's `style` says how its new code sits against the quote style (`Style/StringLiterals`) inferred from the unchanged code around it, pooled across its method, class, file and directory (as it was before the change, so the change's own new code never backs the norm it is judged by) with the nearest weighted most, each scope's counts reported in `evidence` (schema change: `evidence` replaces `surrounding`): `aligned`, `converging` (`normalizing` toward the norm, or `renorming` when the whole scope moved), `diverging` or `abstain`, with each deviation's line, column and a unified-diff fix in the file's own line endings; deviations on one line, of any norms, share one fix that applies them all. A string carried over or edited in place keeps its quotes and isn't judged, nor is code the change deletes in one place and adds back in another (a moved method). A norm needs a pooled share of at least `--norm-threshold` (default 0.8; a lone scope needs `(n + 1) / (total + 2)`); with none inferred, `.rubocop.yml`'s configured style is expected, and both are always reported. A norm is `restyle` when the hunk's `restyle` part respells its variant, and a restyle away from the norm is `flagged`. Generated, vendored and docs files are skipped. `shapr norms PATH...` (files or directories; none is `.`) reports a codebase's norms with no diff: one `norm` record per norm pooled over every file, with `adherence` (`matching` of `judged`) and its deviations by `file` and line; `hotspot` records ranking files, classes and methods by the norms they break, then deviations per 100 lines; and `step` records, a cleanup plan ordered by risk tier (layout, lexical restyles, renames) then adherence gained per line touched, each step a norm's guarded edits as `git apply`-ready diffs (a path holding a quote, backslash or control character quoted in the headers as git quotes it), written to apply in order, so each tier's pull request classifies as `format_only` or `restyle`. Where `.rubocop.yml` sets a style, a norm's `config` says how far the code is from it, how much config doesn't check, and whether `.rubocop_todo.yml` lists the cop; where config and code disagree the plan moves neither. A deviation config doesn't check (a `.rubocop_todo.yml` exclude, a disable comment) gets no edit, counts as the step's `withheld` and ranks no hotspot. Schema change: `norm` records are per norm, not per file and norm (no `file`; each deviation carries its `file`).
- Experimental: `summary.config_trajectory` says, per norm config sets in a changed file, whether the change adds or removes offenses against the configured style (`toward`, `away`, `level`), as counts, not per-line offenses, with the offenses it fixes and adds (`fixed`, `added`) so opposite moves don't hide behind `level`.
- Experimental: norms read `.rubocop.yml` and the directory's untouched files from the revision a range ends in, or a GitHub change's head, so a historical or remote change is judged against its own config; the working tree only when the change ends there. Config shapr doesn't read is named in one stderr line each, and under `shapr norms` in `summary.config_unread`: a gem's (`inherit_gem`, as installed gems vary by machine), a missing or remote `inherit_from`, one that closes a cycle or passes 32 config files in the chain, lines that aren't YAML it reads, a path pattern standing for over 256 brace alternatives (which, unread, counts against the file), an `.editorconfig` section whose glob passes 1024 characters or whose matching (glob characters times path characters, over a file's sections) passes 1,000,000, and a `.rubocop.yml` or `.editorconfig` over 1 MiB. Read from the working tree, a symbolic link is followed only where it resolves inside the repository: config, neighbors, and `shapr norms`' files (one that leaves it is skipped as `unsupported`). A file or line RuboCop wouldn't check for a cop (`AllCops` or the cop's `Exclude`, outside its `Include`, under `# rubocop:disable` or `# rubocop:todo`) gets no configured style and no suggested edit for that norm; the code's own inferred norm still judges it.
- Experimental: the `Layout/SpaceInsideHashLiteralBraces` norm, `space` or `no_space` inside a hash literal's braces.
- Experimental: the `Style/TrailingCommaInArrayLiteral` and `Style/TrailingCommaInHashLiteral` norms, a trailing comma or none in a multiline literal with an item per line; a trailing comma in a one-line literal (or call) is its own style, `single_line_comma`, an offense under every style as in RuboCop.
- Experimental: the `Style/TrailingCommaInArguments` norm, the same for a multiline call's arguments, apart from literals.
- Experimental: the `Style/HashSyntax` norm, `ruby19` labels or `hash_rockets`, per pair.
- Experimental: the `Layout/IndentationConsistency` norm, methods after `private` or `protected` at the modifier's column or a step deeper.
- Experimental: `.editorconfig` configures norms beside `.rubocop.yml`, which wins where both set one. The `Layout/TrailingWhitespace` norm, configured by `trim_trailing_whitespace`.
- Experimental: the `Layout/TrailingEmptyLines` norm, how a file ends, configured by `insert_final_newline`. A suggested edit marks a last line with no line break as unified diffs do.
- Experimental: the `Layout/IndentationWidth` norm, a body's indentation in spaces, configured by RuboCop's `Width` or `.editorconfig`'s `indent_size`.
- Experimental: the `Naming/MethodName` norm, `snake_case` or `camelCase` method names; a rename is suggested only for a private method whose calls are all in the hunk, and only when no other file of the repository holds its name or the new one (a subclass elsewhere may call it; a method elsewhere by the new name would be overridden).
- Experimental: the `Naming/VariableName` norm, `snake_case` or `camelCase` local variables, with a rename when every mention of the local is in the hunk.
- Experimental: the `Layout/SpaceAroundOperators` norm, whitespace on both sides of binary operators, assignments and `=>`; two or more spaces after an operator are their own style (`extra_space`) unless they align, as RuboCop's `AllowForAlignment` reads it.
- Experimental: the `Layout/EmptyLineBetweenDefs` norm, one blank line between adjacent method definitions, two or more (`empty_lines`, as RuboCop's `NumberOfEmptyLines` counts them), or none; as in RuboCop, a gap with blank lines on both sides of a comment isn't judged.
- Cost follows the change more than the repository: file contents come through one long-lived `git cat-file --batch`, a repository search greps once per name and parses each file it finds once, only files calling a dispatch word (`send`, `define_method`, ...) are parsed for computed names, and no per-hunk step walks the whole file.
- `--completions [SHELL]` prints a completion script for bash, zsh, fish, elvish or PowerShell.
